    Using the SDK in a web app

    Since 3.1.0 the package has a browser build. Bundlers that honour the browser export condition (Vite, webpack 5, esbuild with platform: "browser", and the frameworks built on them) pick it up by themselves, with no alias. This guide covers what is different in a browser: loading the cryptography, getting keys from a wallet, and what the user sees.

    A complete app to copy from is in examples/vite.

    Install

    npm install @softseco/confidential-transfers @solana/kit @solana/wallet-account-signer

    The cryptography is WebAssembly

    Proofs and encryption run in @solana/zk-sdk, which is WebAssembly (about 2.7 MB, and it does not compress much). The SDK loads it on the first call that needs it. To start the download as soon as the page opens, call this once at startup:

    import { initConfidentialTransfers } from "@softseco/confidential-transfers";

    void initConfidentialTransfers();

    The browser fetches index_bg.wasm from next to the zk-sdk module. Vite and webpack 5 see that reference and copy the file into your build:

    • webpack 5: nothing to configure.

    • Vite: nothing to configure for vite build. For the dev server, add this to vite.config:

      export default defineConfig({
        optimizeDeps: { exclude: ["@solana/zk-sdk"] },
      });

      Without it the dev server pre-bundles zk-sdk into another folder and the .wasm request fails. In a monorepo, or with the SDK linked from a local folder, the dev server may also refuse the file (HTTP 403) because it is outside your project: add that node_modules folder to server.fs.allow.

    • Anything else (esbuild, for example, does not copy it): serve node_modules/@solana/zk-sdk/dist/web/index_bg.wasm yourself and say where it is:

      await initConfidentialTransfers({ wasmUrl: "/zk/index_bg.wasm" });

    If the file does not load, the SDK throws an error that says so and names these fixes.

    Tested in Chromium: Vite 8 (production build and dev server, in CI on every push) and webpack 5 (production build). The keys a browser derives are byte-for-byte the ones Node derives.

    Keys from a wallet

    The confidential keys (ElGamal and AES) come from the wallet's signature over one fixed message, solana-conf-bal/v1. A wallet signs it through Wallet Standard's solana:signMessage. Ask for that signature once, keep the keys in memory, and pass them to every call as keys:

    import { createSignerFromWalletAccount } from "@solana/wallet-account-signer";
    import { deriveConfidentialKeys, decryptBalance, transfer } from "@softseco/confidential-transfers";
    import { isMessageSigner } from "@solana/kit";

    const signer = createSignerFromWalletAccount(uiWalletAccount, "solana:devnet");
    if (!isMessageSigner(signer)) throw new Error("This wallet cannot sign messages");

    // One wallet prompt: "sign this message".
    const keys = await deriveConfidentialKeys({ signer });

    // No more message prompts: the keys are passed in.
    const balance = await decryptBalance({ rpc, owner: signer, mint, keys });
    await transfer({ rpc, rpcSubscriptions, payer: signer, owner: signer, mint, destinationOwner, amount, keys });

    Without keys, every call asks the wallet to sign the message again. That works, but the user gets one extra prompt per call.

    With React, @solana/react gives you the two signers as hooks:

    const messageSigner = useWalletAccountMessageSigner(account);
    const signer = useWalletAccountTransactionSigner(account, "solana:devnet");

    const keys = await deriveConfidentialKeys({ signer: messageSigner });
    await configureAccount({ rpc, rpcSubscriptions, payer: signer, owner: signer, mint, keys });

    What to know about the keys:

    • They belong to the wallet, not to a mint: one set reads every confidential account the wallet owns. They are the same keys the spl-token CLI and other standard clients derive.
    • They cannot move funds (that needs the wallet's transaction signature), but they decrypt every balance and amount of the wallet. Keep them in memory for the session. Do not put them in localStorage; after a reload, ask for the signature again.
    • Before it decrypts a balance or builds a proof, the SDK checks that the keys match the account's ElGamal key, so keys from the wrong wallet fail with a clear error instead of wrong numbers.

    What the wallet must support

    • solana:signMessage, signing the message as given. The SDK verifies the signature and refuses a wallet that changes the message, because the keys would then differ from the standard ones.
    • solana:signTransaction. A wallet that only offers signAndSendTransaction cannot be used yet, because the SDK simulates each transaction before sending it.

    Phantom, Solflare and Backpack support both. When a wallet cannot sign messages, the SDK's error says so; you can check up front with isMessageSigner(signer) or "solana:signMessage" in wallet.features.

    What the user approves

    When the wallet pays the fees and owns the account, it is asked to approve every transaction:

    Step Transactions
    Unlock (deriveConfidentialKeys) none, one message signature
    configureAccount 1
    deposit 1
    applyPendingBalance 1
    transfer 5 (proof accounts, the transfer, closing the proof accounts)
    withdraw 4

    A transfer with five prompts is the main rough edge in a browser today. Approving them in one prompt is planned for 3.2.

    Testing

    test/browser/e2e.ts runs examples/vite in Chromium with a Wallet Standard test wallet against a local validator: connect, unlock, set up, deposit, apply, transfer, withdraw, then checks the balances and that the wallet signed the key message exactly once. CI runs it on every push. To run it yourself, see CONTRIBUTING.md.
